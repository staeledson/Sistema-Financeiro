# Fase 15 — Deploy (front na Vercel pessoal, back-end na Railway) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publicar o sistema para uso pessoal: front Vue na **Vercel pessoal** do usuário, e API, worker, Postgres, Redis e armazenamento de arquivos na **Railway** (conta pessoal), com cadastro de usuários fechado, saúde monitorada e um passo a passo que o usuário consegue seguir sozinho.

**Architecture:** O navegador fala só com a origem da Vercel; um `rewrite` da Vercel repassa `/api/*` para a API na Railway (mesma origem para o navegador: sem CORS, o mesmo modelo do proxy do Vite em desenvolvimento). Na Railway rodam dois serviços do mesmo repositório (API e worker, mesma imagem Docker, comandos de partida diferentes) mais os plugins Postgres e Redis e um bucket S3. As migrations rodam no `preDeploy` da API. Os segredos são cadastrados **pelo usuário** nos painéis; este plano só produz código, configuração e o roteiro.

**Tech Stack:** Docker, Railway (config as code), Vercel (`vercel.json`), NestJS/Fastify, Better Auth, Prisma 7 (`migrate deploy`), BullMQ.

## Global Constraints

- **Conta Vercel: somente a pessoal.** O conector de Vercel desta sessão está autenticado no time da empresa (`pluralmed's projects`): **não usar** (nem listar, criar, configurar ou fazer deploy por ele). Nada de `vercel`/`railway` CLI sem o usuário logado na conta pessoal e confirmando cada ação que cria recurso ou custa dinheiro.
- **Segredos nunca passam por mim.** `BETTER_AUTH_SECRET`, `OPENROUTER_API_KEY`, `GROQ_API_KEY`, chaves do bucket e VAPID são digitados pelo usuário nos painéis da Railway/Vercel. O repositório é **público**: nada de segredo, nem de dado pessoal, em arquivo versionado (incluir exemplos só com marcadores).
- A API **não** tem prefixo `/api` (o Vite/Vercel reescreve `/api/:path*` → `/:path*`); a exceção é o Better Auth em `/api/auth/*`, que mantém o prefixo. O web usa `VITE_API_URL || "/api"` e em produção fica com o padrão `/api`.
- Cadastro aberto na internet é inaceitável: em produção só emails de uma lista de permissão criam conta (`SIGNUP_ALLOWED_EMAILS`). Sem a variável (desenvolvimento e testes) o comportamento atual não muda.
- A API escuta `0.0.0.0:$PORT`. O worker não expõe porta. Nenhum serviço precisa de disco local (PDFs e imagens vão para o bucket).
- Redis do BullMQ precisa de política `noeviction`; usar `REDIS_URL` privada da Railway (rede interna) e `maxRetriesPerRequest: null` (o worker já faz).
- Mensagens e documentação em português do Brasil.
- Verificação local obrigatória antes de pedir ao usuário para publicar: imagem Docker construída e rodando contra o Postgres/Redis do `docker-compose.yml` (portas 5433/6380), com `GET /health` respondendo e o login funcionando.
- Testes e2e da API compartilham o banco `financas` e não rodam em paralelo com outro e2e nem com `pnpm dev`.

## Decisões

1. **Rewrite na Vercel em vez de CORS.** O front usa `/api` como hoje; `apps/web/vercel.json` reescreve para a URL pública da API (conhecida só depois do primeiro deploy na Railway, então o arquivo é ajustado e commitado na Task 5). Risco conhecido: o proxy da Vercel pode limitar o tamanho do corpo; os uploads de extrato (PDF/CSV/OFX em base64) ficam muito abaixo de 4,5 MB. Se algum dia falhar, o plano B é `VITE_API_URL` apontando direto para a API + `app.enableCors` (não implementado agora).
2. **Better Auth:** `BETTER_AUTH_URL` = origem pública do **front** (é a origem que o navegador vê); `TRUSTED_ORIGINS` (lista separada por vírgula) acrescenta origens extras (ex.: domínio próprio depois). O baseURL já é confiável por padrão.
3. **Uma imagem, dois serviços.** `Dockerfile` na raiz instala tudo (incluindo `devDependencies`, necessárias ao runtime com `@swc-node/register` e `tsx` e à CLI do Prisma) e gera os dois clientes Prisma; a API parte com `pnpm --filter @app/api start:prod` e o worker com `pnpm --filter @app/worker start:prod`. Sem etapa de build do TypeScript (o repositório roda direto do código-fonte via swc/tsx, como em desenvolvimento).
4. **Armazenamento:** bucket S3-compatível da própria Railway (variáveis `MINIO_*` já suportam qualquer S3 com `forcePathStyle`); Cloudflare R2 como alternativa. A API sobe mesmo sem bucket (o `onModuleInit` ignora a falha); só ingestão por imagem/áudio/PDF-IA depende dele.
5. **Backups:** o Postgres da Railway é a única cópia dos dados financeiros: a Task 4 documenta backup periódico (`pg_dump` agendado/local) e a restauração; é requisito do roteiro, não opcional.
6. **Fora de escopo:** domínio próprio, CI de deploy além do deploy automático por push (Railway e Vercel já fazem), monitoramento além do healthcheck, `enableCors`, multi-região.
